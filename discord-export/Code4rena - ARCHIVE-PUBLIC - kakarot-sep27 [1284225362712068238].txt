[09/30/2024 14:51] fcremo
Once the devcontainers were up and running, I used two terminals:
- run `make run-katana` ,
- the other one `make test`
I used [these instructions](https://github.com/kkrt-labs/kakarot/blob/main/docs/CONTRIBUTING.md#setting-up-the-environment) as guidance.

Tip to save time: you can avoid running all the tests every single time by specifying a more precise path in the commands
```
uv run pytest tests/src -m "not NoCI" --log-cli-level=INFO -n logical --seed 42
uv run pytest tests/end_to_end --seed 42
```
which is [what `make test` runs](https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/Makefile#L42)


[09/30/2024 14:52] fcremo

[09/30/2024 15:15] fcremo
There are a couple of aspects I'd like to put a spotlight on; I've already mentioned them in the catalyst doc, but I feel like they are important enough to warrant bringing them up explicitly


[09/30/2024 15:15] willbdeving
👀


[09/30/2024 15:19] fcremo
The first is, I encourage you to look at the early parts of the transaction flow, specifically the entrypoint into the account contract. This is mainly because it was refactored after our audit.


[09/30/2024 15:20] fcremo
In the commit we reviewed, account contracts natively supported the account abstraction `__verify__` and `__execute__` entrypoints; this is not the case anymore, and a bug in there could easily be a high severity issue (e.g. sig bypass or denial of service).


[09/30/2024 15:22] fcremo
Another interesting idea is differential fuzzing the interpreter vs. geth (or another EVM implementation).

It's something I would have really liked doing, but didn't get a chance to, as our audit prioritized a manual code review of the whole codebase.

Despite Kakarot passes (a majority of) the official ethereum foundation compliance tests, we still found two (IIRC) opcode semantics bugs which were not covered by the testsuite (!).

I'm convinced both would have been found by differential fuzzing.


[09/30/2024 15:26] fcremo
I think achieving good performance could prove a challenging engineering effort, mostly because I'm not sure how efficient the Cairo0 code can be made to run.

On the plus side, the executor component of the differential fuzzer could prove useful for hunting bugs in other Cairo0 (and perhaps even Cairo1) projects, so it could be a worthwile investment.

Obligatory disclaimer: this is not ~~financial~~ time investment advice 😛

[09/30/2024 15:31] fcremo
The class of bugs where I **will** be surprised if there aren't any issues is arithmetic overflows/underflows.

Cairo0 is, frankly, really unforgiving in this regard (just as many others, e.g. good 'ol C).
